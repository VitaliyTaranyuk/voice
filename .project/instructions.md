# Git Workflow и правила разработки проекта

## Цель

Настоящая инструкция определяет обязательные правила разработки проекта, работы с Git и GitHub, управления ветками, тестирования и интеграции изменений. Все участники разработки и ИИ-ассистенты (Cursor, Claude Code и другие) обязаны соблюдать данные правила.

---

# 1. GitHub является источником истины

Каждый проект имеет собственный удалённый репозиторий GitHub.

Если локальный проект называется:

```
Voice/
```

то удалённый репозиторий также должен называться:

```
Voice
```

Локальный проект всегда должен быть подключён только к соответствующему удалённому репозиторию.

GitHub считается основным источником истины. Локальная копия является рабочим состоянием проекта.

---

# 2. Все изменения находятся под контролем версий

Любые изменения должны фиксироваться в Git.

Запрещается длительная разработка без истории изменений.

История должна позволять:

* восстановить любое состояние проекта;
* определить причину каждого изменения;
* быстро выполнить откат;
* анализировать изменения между версиями;
* безопасно вести параллельную разработку;
* использовать GitHub как резервную копию проекта.

---

# 3. Каждая задача — отдельная ветка

Любая задача, независимо от её размера, начинается с создания отдельной ветки.

Запрещается выполнять разработку непосредственно в `main`, `master` или основной ветке проекта.

Даже небольшие исправления оформляются отдельной веткой.

Название ветки должно отражать назначение задачи.

Например:

```
feature/auth
feature/voice-search
feature/payment
fix/login
fix/cache
refactor/database
docs/api
```

Если задача оказывается слишком большой, она должна быть предварительно декомпозирована на несколько независимых подзадач. Для каждой подзадачи создаётся отдельная ветка.

Размер ветки должен быть минимально возможным. Один Pull Request — одна законченная логическая задача.

---

# 4. Рабочий цикл разработки

Каждая задача проходит следующий цикл:

1. анализ задачи;
2. декомпозиция при необходимости;
3. создание отдельной ветки;
4. реализация изменений;
5. локальная проверка;
6. запуск автоматических тестов;
7. запуск тестов смежного функционала;
8. исправление обнаруженных проблем;
9. создание коммита;
10. Push ветки;
11. создание Pull Request;
12. ожидание подтверждения Merge.

Пропуск этапов не допускается.

---

# 5. Автоматические проверки

Перед публикацией изменений Cursor обязан автоматически выполнить:

* форматирование кода;
* линтер;
* статический анализ;
* сборку проекта;
* проверку успешности сборки;
* запуск всех тестов, относящихся к изменённому модулю;
* запуск тестов смежных модулей, которые потенциально затрагиваются изменениями;
* проверку отсутствия регрессий;
* запуск приложения (если это возможно);
* проверку успешного запуска.

При наличии ошибок публикация изменений запрещается.

---

# 6. Проверка влияния изменений

Каждое изменение рассматривается не только как изменение собственного модуля.

Перед публикацией необходимо проверить:

* зависимости;
* импортируемые библиотеки;
* интерфейсы;
* API;
* соседние модули;
* общий Build проекта;
* обратную совместимость.

Если существует вероятность регрессии, соответствующие тесты становятся обязательными.

---

# 7. Автоматическая работа Cursor

После каждого изменения Cursor должен автоматически:

* сохранить файлы;
* выполнить форматирование;
* выполнить линтер;
* выполнить сборку;
* выполнить тестирование;
* проверить успешность выполнения всех операций;
* сообщить о найденных ошибках.

Все действия выполняются автоматически без дополнительных запросов пользователю.

---

# 8. Работа с Git

После успешного прохождения всех проверок Cursor может автоматически:

* создать Commit;
* сформировать информативное сообщение Commit;
* выполнить Push текущей ветки.

Коммиты должны быть небольшими и логически завершёнными.

История должна оставаться понятной и читаемой.

---

# 9. Pull Request

После успешного Push Cursor может автоматически создать Pull Request.

Перед созданием Pull Request необходимо убедиться, что:

* отсутствуют конфликты;
* Build успешен;
* тесты успешно завершены;
* требования задачи выполнены;
* описание Pull Request содержит краткое описание изменений.

---

# 10. Merge

Cursor не имеет права самостоятельно выполнять Merge.

Merge выполняется исключительно после явного подтверждения пользователя.

Если пользователь прямо не написал:

* выполнить Merge;
* смержить;
* объединить Pull Request;

Cursor обязан оставить Pull Request открытым.

---

# 11. Запрещённые действия

Без явного разрешения пользователя запрещается:

* Merge;
* Force Push;
* Rebase опубликованных веток;
* `git reset --hard`;
* удаление веток;
* изменение удалённого репозитория;
* удаление тегов;
* переписывание истории;
* публикация изменений в другой репозиторий;
* выполнение потенциально необратимых операций.

Во всех неоднозначных ситуациях выбирается наиболее безопасный вариант.

---

# 12. Документация проекта

Все правила проекта должны храниться внутри репозитория.

Рекомендуемая структура:

```
.project/
    instructions.md
    architecture.md
    conventions.md
    workflows.md
    decisions.md

docs/
```

Документация должна находиться под контролем версий.

Любые архитектурные решения должны документироваться одновременно с их внедрением.

---

# 13. Приоритет инструкций

При выполнении задач Cursor обязан использовать следующий порядок приоритета:

1. документация текущего репозитория;
2. инструкции проекта;
3. конфигурация проекта;
4. глобальные пользовательские инструкции.

Локальная документация всегда имеет более высокий приоритет.

---

# 14. Качество изменений

Cursor обязан стремиться не только к выполнению поставленной задачи, но и к сохранению качества проекта.

Перед завершением работы необходимо оценить:

* влияние изменений на архитектуру;
* влияние на производительность;
* читаемость кода;
* соответствие существующему стилю проекта;
* отсутствие дублирования;
* возможность упрощения решения;
* соблюдение принципов SOLID, DRY, KISS и YAGNI там, где это оправдано;
* наличие технического долга, создаваемого изменениями.

Если обнаруживается решение, которое существенно повышает качество проекта без неоправданного увеличения сложности, оно предпочтительно.

---

# 15. Основной принцип

Любое изменение должно быть:

* изолированным;
* обратимым;
* протестированным;
* документированным;
* воспроизводимым;
* безопасным для интеграции;
* понятным другим разработчикам.

Каждая завершённая задача должна быть готова к включению в основную ветку без дополнительных доработок, а история проекта должна позволять восстановить любую предыдущую версию и объяснить происхождение каждого изменения.
